# ADR-001 — Modelling policy for mutation-bearing entities on the HCD Data API

**Status:** Proposed
**Date:** 17 September 2026
**Deciders:** David Leconte (author) · engagement architect on any HCD Data API design · whoever owns the client's data model
**Evidence base:** `findings.json` / `rapport_verification.md` — run 1 record 2026-09-17T14:59:03Z, query traces 15:02Z, replication run 15:05:49Z, on `alphadebunker`
**Supersedes:** nothing. **Superseded by:** nothing yet — see *Revisit triggers*.

---

## Context

### The measurement that forces this decision

A verification run against IBM DataStax HCD 2.0.6 (`nodetool version` = 5.0.7.0-ea50e91ba01f) with Data API v1.0.33 established two facts about the write path that are not published in any vendor documentation.

**Fact 1 — the read-modify-write cycle exists.** With tracing enabled, every `updateOne` carrying a single `$set` produced exactly two CQL statements: a `SELECT key, tx_id, doc_json WHERE key = ?`, then one `UPDATE` rewriting nine derived columns, `tx_id` and the whole `doc_json` — eleven assignments — guarded by `IF tx_id = ?`. Observed 10/10. Statement counts per operation: `insertOne` = 1, `updateOne` = 2, `deleteOne` = 2.

**Fact 2 — and this is the one that drives the decision — the cost of a mutation scales with the amount of *indexed content* the document carries and the mutation never touches.** The protocol grew indexed-field count (1 → 17) and indexed bytes (≈ 8 KB → 136 KB) together, so it does not separate a per-field from a per-byte cost; the mutation itself was held constant at one scalar field throughout. **This per-byte rate is a MEMTABLE/cache figure (audit I4):** M15 later showed that when the read half of the cycle is forced onto SSTables, the per-byte growth flattens (×5.94 → ×1.52) and a large fixed read-path cost dominates. The mechanism of section 3 (read-modify-rewrite) holds; the numeric rate below does not transfer to a disk-bound read.

| Indexed ballast fields × 8 000 B (document size) | p50 latency of a one-field `$set` |
|---|---|
| 1 (1 KB) | 12.1 ms |
| 17 (128 KB) | 90.8 ms |
| **growth** | **×7.50** |

Over the same range the read control grew ×1.56 and the HTTP request payload was constant (122–124 bytes request, 47 bytes response, at every document size). The growth is therefore not wire cost and not read cost. It is the rewrite of derived columns and the maintenance of storage-attached indexes over content that was never touched.

By contrast, growing the *unindexed* payload of a document by ×128 grew update latency only ×1.92, against a read control of ×1.86 (×2.21 against ×1.94 on the replication run) — a difference the latency probe alone could not resolve, which is why Fact 1 rests on the trace rather than on the curve.

### Why this is an architecture decision and not a tuning note

Automatic indexing is the Data API's headline convenience: any field becomes filterable with no index declaration and no migration. The measurement establishes that this convenience is charged per write, in proportion to the indexed content of the document, on every mutation regardless of what was mutated. On a collection created with defaults, nine storage-attached indexes are created automatically, and the platform's own guardrails are `sai_indexes_per_table_fail_threshold = 10` and `sai_indexes_total_fail_threshold = 100` — the latter a ceiling **per node, across all keyspaces**, not per keyspace.

Two consequences follow immediately and neither is a knob:

- **Write cost is a function of the indexed byte volume** (M11), and it is charged in two places (M12): about seventy per cent in the stateful storage engine — the SELECT, the conditional UPDATE, the storage-attached index maintenance — and about a quarter to a third in the stateless Data API tier that parses, shreds and serialises. A team that adds indexed content is buying write latency whether or not it ever writes to those fields; the majority of that latency sits in the component that does not scale out by adding instances, which is why this stays an architecture decision and not a tuning note. The minority that does scale out is real and worth naming, but it does not move the centre of gravity.
- **Collection density is bounded.** Nine indexes per non-vector collection against a total ceiling of one hundred gives roughly eleven collections per node before the guardrail refuses. A vector collection is expected to consume a tenth index, at the per-table threshold; this was not measured in the run and is action item 2.

A third constraint shapes the options: the Data API refuses any **indexed** string longer than 8 000 bytes (`SHRED_DOC_LIMIT_VIOLATION` observed at 8 192 bytes; 8 000 accepted). Large text therefore *must* be excluded from indexing, which means selective indexing is not merely available — for some payloads it is mandatory.

### Forces in tension

| Force | Pulls toward |
|---|---|
| Schema velocity early in a product's life | index everything; no migration to add a predicate |
| Write latency on mutation-bearing entities | index narrowly |
| Index budget (10 per table, 100 per node across all keyspaces) | index narrowly; fewer, denser collections |
| 8 000-byte indexed-string limit | exclusion is compulsory for large text |
| Operational simplicity | one collection per entity, defaults everywhere |
| Correctness under concurrency | keep the `tx_id` guard, i.e. keep using the conditional path |

---

## Decision

**Classify every entity at design time by its mutation profile, and apply an indexing policy per class rather than accepting the default globally.**

Concretely: adopt **Option B as the default for all entities, escalating to Option C for entities that are both wide and frequently mutated**, and treat Option D as the answer for record types whose shape is stable.

The classification is cheap and takes place before a line is written:

| Class | Test | Policy |
|---|---|---|
| **Append-dominant** | written once, read many, rarely mutated | Default indexing. The convenience is free here: you pay index maintenance once per document, at insert. |
| **Mutation-bearing, narrow** | little indexed content on the mutation path (an order of magnitude, not a measured bound: a handful of short indexed fields), mutated often | Default indexing acceptable; measure before assuming. |
| **Mutation-bearing, wide** | much indexed content — many fields, or long indexed strings — mutated often: status machines, counters, hot aggregates | Selective indexing (B), and split (C) if the mutable subset is small relative to the whole. |
| **Stable shape, key-and-range access** | ledgers, event trails, time series | Data API tables (D), not collections. |

---

## Options Considered

### Option A — Default indexing everywhere (status quo)

| Dimension | Assessment |
|---|---|
| Complexity | Lowest — nothing to decide, nothing to declare |
| Write cost | Highest, and grows silently with indexed content (×7.50 measured, 1→17 indexed 8 000-byte fields — a **memtable-regime** figure; it flattens to ×1.52 when the read is disk-bound, M15/I4) |
| Index budget | Consumes ~9 per collection; ~11 collections per node |
| Team familiarity | Highest — it is the documented default |
| Failure mode | Degradation is invisible until it is a production incident, and is attributed to the wrong layer |

**Pros:** maximum schema velocity; no design meeting required; no migration to add a predicate.
**Cons:** write latency is coupled to indexed content rather than to write pattern; the coupling is undiscoverable without instrumentation; the 8 000-byte limit makes it unusable for documents carrying large text.

### Option B — Selective indexing at collection creation

Declare `indexing: { deny: [...] }` or `{ allow: [...] }` in the collection definition. Excluded fields remain in `doc_json` and remain readable; they simply stop being filterable and stop being maintained on write. The whole `doc_json` is still read and rewritten on every mutation (Fact 1); B removes the index-maintenance term, not the rewrite.

| Dimension | Assessment |
|---|---|
| Complexity | Low — one clause at creation |
| Write cost | Proportional to the indexed subset, which is now a decision rather than an inheritance |
| Index budget | Reduced per collection; more collections fit under the 100 ceiling |
| Team familiarity | Moderate — the clause is not widely used and is easy to forget |
| Failure mode | A field excluded in error is not filterable; discovered at query time, not at write time |

**Pros:** directly attacks the measured cost driver; mandatory anyway for strings above 8 000 bytes; per the vendor's Astra documentation the indexing options are fixed at creation (not tested in this run), which forces the decision early — when it is cheap.
**Cons:** requires knowing the query pattern at creation time, which is exactly what teams do not know early; an `allow` list that proves wrong costs a collection rebuild and a backfill.

### Option C — Split by mutability: narrow hot collection, wide cold collection

Hold the frequently mutated fields — status, counters, timestamps — in a narrow collection keyed by the same identifier, and the stable body in a wide one. Mutations touch the narrow collection only.

| Dimension | Assessment |
|---|---|
| Complexity | Moderate to high — two writes on creation, a join in the application, two identifiers to keep consistent |
| Write cost | Lowest for the mutation path; the wide document is never rewritten by a status change |
| Index budget | Consumes two collections' worth of indexes for one entity — roughly 18 of the 100 per node |
| Team familiarity | Low — this is a deliberate denormalisation that reads as an anti-pattern to a document-database audience |
| Failure mode | Consistency between the two records is the application's problem: atomicity is per document, and there is no cross-document transaction here (`HCD does not adhere to ACID transactions with rollback or locking mechanisms`) |

**Pros:** removes the coupling entirely rather than reducing it; the hot path becomes a narrow document where the measured coefficient is near its floor.
**Cons:** buys write performance with correctness risk, and the correctness risk is the harder engineering problem. Consumes index budget at double rate. Justified only when the measured cost is actually hurting.

### Option D — Data API tables instead of collections

For records of stable shape accessed by key and range, use schema-defined tables with an explicit `primaryKey` / `partitionBy` / `partitionSort`, reached through the same JSON API.

| Dimension | Assessment |
|---|---|
| Complexity | Moderate — a schema must be declared and evolved |
| Write cost | Indexes are declared, not inherited; cost is explicit by construction |
| Index budget | Explicit and controlled |
| Team familiarity | High for anyone with relational or CQL background; low for document-first teams |
| Failure mode | Schema migration on shape change; partition design errors surface late (the 100 000-row / 100 MB bounds) |

**Pros:** the cost model becomes legible; partition bounding becomes possible and is the right tool for ledgers and event trails.
**Cons:** loses the schemaless velocity that motivated the Data API; tables via the Data API carry a public-preview designation, which matters for a client commitment. On the build measured here, `createTable` answers `TABLE_FEATURE_NOT_ENABLED` — the feature is a flag, off by default in Data API v1.0.33 (observed 4 September 2026 on the same stack, outside this run) — so Option D requires an explicit configuration change before it is available at all. Both points belong in the risk register.

### Option E — A different engine for the mutation-heavy component

Route counters and hot status machines to a store whose update path is targeted rather than decomposing.

| Dimension | Assessment |
|---|---|
| Complexity | Highest — a second system to operate, secure and reason about |
| Write cost | Lowest for that component |
| Team familiarity | Varies |
| Failure mode | Operational surface doubles; consistency between stores is now a distributed problem |

**Pros:** structurally correct for a workload the decomposing engine is not built for.
**Cons:** the overhead is rarely justified by one component, and the decision is frequently taken on an unmeasured intuition. Reach for it only after B, C and D have been measured and found insufficient — and state plainly that this option exists, because pretending otherwise is the kind of advocacy that destroys a technical reputation.

## Trade-off Analysis

**The measured coefficient is the whole argument for B.** ×7.50 from 1 to 17 indexed 8 000-byte fields, on a constant mutation, with constant wire payload, is large enough that it changes designs rather than tuning them — for that document shape, **and in the memtable/cache regime only** (it flattens to ×1.52 once the read is disk-bound, M15/I4); whether seventeen short indexed fields cost the same is not established. No other option is needed to capture most of that: B is one clause, it is fixed at creation — which is a feature, since it forces the decision while it is cheap — and it is compulsory for large text regardless.

**C buys the rest of the gain with a correctness liability.** Splitting eliminates the coupling instead of reducing it, but atomicity on this platform is per document; two records for one entity means the application owns the invariant. That is a real engineering cost and it is easy to underestimate in a design review where the latency number is on the slide and the invariant is not. C is justified when B has been applied and measured and the mutation path still dominates.

**D is not a fallback; it is the right answer for a different class.** The temptation is to treat tables as a retreat from collections. They are not. For a ledger or an event trail, the shape is stable, the access is by key and range, and the partition bounds matter more than schema velocity. The public-preview designation and the disabled-by-default flag are the genuine obstacles for a client commitment, and they belong in the risk register rather than in the technical comparison.

**What none of the options addresses.** The conditional-write guard (`IF tx_id = ?`) is not optional and is not a cost any of these options removes. Every mutation observed carried a conditional statement, at `LOCAL_SERIAL`, and every statement ran at `LOCAL_QUORUM` — both measured on this build. On the RF = 1 topology first measured, those levels are satisfied by a single replica: the names were established, the multi-replica cost was not. The RF = 3 run (action item 3, evidence M5) closed that gap: the conditional path does carry a full three-replica Paxos round, and its coordinator-side cost is about twice a non-conditional read (13.7 ms vs 6.6 ms p50) — higher than anything in the RF = 1 record, and in a direction none of these options improves.

## Consequences

**What becomes easier**
- Write cost becomes a design variable rather than an emergent property. A reviewer can ask "how many indexed bytes sit on the mutation path?" and get an answer (M11: byte volume drives the cost; field count is a weak secondary factor).
- Index budget planning becomes arithmetic: indexed fields per collection against the 10-per-table and 100-per-node thresholds.
- The failure mode from the article's opening — latency creeping upward because fields were added — is caught at design time by classification rather than at 3 a.m. by instrumentation.

**What becomes harder**
- Every new entity now requires a classification decision before it is created, and the decision is expensive to reverse: per the vendor's documentation an `allow`/`deny` list is fixed at collection creation (not tested here), so a wrong call costs a rebuild and a backfill.
- Teams lose some of the schemaless velocity that motivated the platform choice. That is the trade being made deliberately, and it should be named as such to the client rather than presented as a free optimisation.
- Option C introduces a cross-document invariant the application must hold, on a platform that offers no cross-document transaction.

**What we will need to revisit**
- Every number here comes from **one node at RF = 1, entirely memtable-resident, zero SSTables flushed, no compaction cycle crossed, client on loopback, `commitlog_sync periodic 10 s`**. The ×7.50 coefficient is a memtable-regime figure for one document shape (17 × 8 000-byte indexed strings). Under a disk-bound regime with real replication, or with many short indexed fields, it may be larger, smaller, or differently shaped. **No client commitment should be made on this coefficient alone.**
- The consistency levels observed are the Data API tier's own defaults on v1.0.33. Whether they are configurable was not tested.
- Nothing here transposes to Apache Cassandra 5.0.x or 6.0, to another HCD or Data API version, or to any other vendor's product.
